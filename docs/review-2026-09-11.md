## 재현 범위와 해석

- search 독립 실행: `.venv/bin/python -m pytest -p scripts.verify tests/unit/search --no-cov` → **수집 오류 5건, 실행된 테스트 0건**. memory 독립 실행은 **49 PASS**, medical_api 독립 실행은 **32 PASS**였다. 이 결과는 각 모듈의 통합 성공을 의미하지 않는다.
- R5의 검색 메서드와 R10의 `is_stale()`는 import 오류 때문에 AST에서 관련 원문 함수만 분리해 실행했다. 파일을 수정하거나 전체 SearchSession이 정상 생성된 것처럼 취급하지 않았다.
- R6·R7은 설치된 라이브러리와 로컬 가짜 모델/도구를 사용한 최소 그래프 재현이다. 프로젝트 전체 runner의 실행 성공이나 실제 LLM 응답을 검증한 결과가 아니다.
- R9는 저장소의 녹화 fixture를 사용했고, R11은 합성 키와 MockTransport만 사용했다. 실제 API 상태와 지연 시간은 측정하지 않았다.
- [agent/conftest.py:22](../tests/unit/agent/conftest.py#L22)는 renderer·memory·SearchSession을 대체하고 `create_agent`도 가짜 그래프로 바꾼다. 이 테스트가 향후 통과하더라도 실제 import, 도구 시그니처, 메시지 전달, HITL 재개 검증을 별도로 유지해야 한다.

## 이후 백엔드 연결 시 수정 순서

1. **실행 가능한 import와 공통 상태부터 맞춘다 — R1~R3.** 1번은 모델·runner, 2·3번은 retry 인터페이스, 4번은 실제 memory 타입과 생명주기, 6번은 renderer/화면 어댑터 경계를 확인한다. 새 프로세스에서 실제 모듈을 import하는 검증을 먼저 통과시킨다.
2. **도구·provider·저장 계약을 연결한다 — R4·R5·R8.** 지역 목록과 병원 ID, 캐시와 강제 갱신, 승인된 방문 계획의 저장 주체를 확정한다. fixture로 병상 조회가 실제 호출되는지와 지역 경계를 넘는 후보가 포함되는지 확인한다.
3. **실제 그래프의 입력·승인 흐름을 고친다 — R6·R7.** 사용자 메시지 전달, 승인 전 저장 0회, 승인 후 1회, 거절·중복 요청 시 추가 저장 0회를 프로젝트 runner로 검증한다.
4. **후보에 쓰는 데이터와 오류 로그를 바로잡는다 — R9~R11.** 녹화 XML의 실제 태그와 값, KST/UTC 시각 비교, 캐시 지연 표시를 확인한다. 키 마스킹은 이후 실제 녹화보다 먼저 완료한다.
5. **Streamlit에서 실제 연결을 다시 검토한다.** 앞선 계약을 통과한 runner를 연결하고 [UI 연결 계약](ui-integration.md)에 따라 조회·119 우선 안내·새 대화·승인/거절·삭제·오류 흐름을 재실행한다. 최신 수치와 남은 차단 사유는 [검증 기록](verification.md)에 갱신한다.
