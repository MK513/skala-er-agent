# 6번 Verification 담당 가이드

현재 화면은 실제 모드 기본값, 의료 API 직접 조회, 연결 상태의 3개 탭으로 확장했다. 아래 시연 순서는 별도 화면 검토용 모드에 해당한다. 실제 runner factory는 백엔드 계약 정리 후 연결한다.

2026-09-11 최신 상태: `main`의 `e97341a`까지 로컬에 반영했다. 1~5번 구현은 모두 병합되었지만 실제 연결에 오류가 남는다. 최신 검증은 **174개 통과 + 수집 오류 6건, 전체 FAIL / 통합 BLOCKED**다. 아래 초기 작업 설명은 `8e996da`에서 시작한 배경이며, 현재 수정 우선순위는 [통합 검토](review-2026-09-11.md), 실행 근거는 [검증 기록](verification.md)을 따른다.

## 지금 상황을 먼저 정확하게 말하기

현재 팀 저장소는 `skala-er-agent`, 작업 브랜치는 `feature/verification`이다. 시작 커밋은 `8e996da`로, 메모리 모듈 PR만 병합된 상태였다. 옆의 `er-agent`와 첨부 발표 자료는 구현 수준이 다른 별도 자료다.

작업 시작 시 1·2·3·5번 코드와 공통 모델/설정, CLI, 벤치마크, fixture 3개는 빈 파일이었다. 자동 테스트 49개는 모두 4번 메모리 테스트였다. 그래서 발표 자료의 140개 통과, 외부 API 연동, 14회 모델 제한, 실제 그래프 데모를 이 저장소 성과로 설명하면 안 된다.

6번의 책임은 **다른 모듈이 연결된 사용 흐름을 재현하고 실패를 발견할 수 있게 만드는 것**이다. 화면, 저장 승인, 세션, 실행 환경, 검증 자동화를 독립적으로 준비했고, 이제 병합된 모듈의 계약 오류를 확인하고 실제 연결을 검증할 단계다.

## Streamlit에서 가장 중요한 원리

버튼을 누르거나 입력하면 스크립트가 위에서 아래로 다시 실행된다. 그래서 에이전트를 매번 만들거나 매 렌더링에서 조회하면 이전 대화가 사라지거나 중복 요청이 발생한다.

이 앱은 `st.session_state["web"]`를 한 번 만들어 보관한다. 렌더링은 저장된 결과를 읽기만 하고, 입력/버튼 이벤트에서만 상태를 바꾼다. 전역 캐시로 사용자 객체를 공유하지 않는다.

Streamlit 콜백은 본문보다 먼저 실행된다. 그래서 설정 변경과 승인 클릭이 같이 들어오는 경우도 검사해야 한다. 단순히 본문에서 설정을 비교해 초기화하는 것만으로는 오래된 승인을 막기에 충분하지 않다.

## 저장 흐름을 설명하는 법

```text
가상 병원 카드 선택
  → PendingVisitPlan 생성
  → 아직 Store 저장 0건
  → 승인 버튼
  → VisitPlanService.decide(approved=True)
  → ERFinderStore.add_visit()
  → 승인 대기 제거, 저장 1건
```

거절하면 `decide(approved=False)`로 끝나고 저장하지 않는다. 승인 대기가 사라진 뒤 같은 결정을 다시 보내도 추가 저장하지 않는다. 이것은 **4번 메모리와 연결한 화면 승인 검증**이다. 실제 LangGraph의 interrupt/resume은 최신 runner에서 별도 오류가 발견되었으며, 수정 후 전체 저장 흐름을 다시 검증해야 한다.

새 대화는 대화·후보·승인만 지우고 동의한 주소/계획은 남긴다. 기록 전체 삭제는 이 브라우저가 소유한 저장소까지 폐기한다. 영구 DB는 없으므로 서버 종료/브라우저 세션 소실 뒤 복구를 보장하지 않는다.

## 3분 시연 순서

1. 기본 `화면 검증용 데모` 모드를 확인하고 “실제 API가 아닌 합성 시나리오”라고 먼저 말한다.
2. `선택한 화면 확인`을 누른다. 가상 응급센터 A/B/C와 거리·병상·갱신 지연 표시를 설명한다.
3. 두 번째 병원을 선택한다. 아직 저장되지 않았음을 `저장한 방문 계획`에서 확인한다.
4. 승인 후 기록에 B가 생긴다. 다시 실행해도 같은 승인으로 기록이 늘지 않는 점을 설명한다.
5. 새 대화는 계획을 남기고, 기록 전체 삭제는 계획까지 없애는 것을 보여준다.
6. `위치 재질문` 시나리오는 첫 입력에 위치 질문, 두 번째 입력에 후보를 표시한다. 실제 자연어 위치 추론이 아닌 고정 2단계 시연임을 말한다.
7. `119 우선 안내`와 `서비스 오류` 화면을 보여준다. 실제 위험 표현 검출 속도/정확도 검증이라고 설명하지 않는다.
8. 실제 모드를 선택하면 연결 대기 안내와 비활성 입력창이 표시된다.

모든 시나리오는 선택된 고정 예시다. 입력을 무시하는 것처럼 보이는 것은 지금 단계의 의도된 동작이다. 실제 증상 판단/주소 해석은 앞으로 연결할 1·3·5번 기능이다.

## Verification 결과를 읽는 법

```bash
uv run --frozen python scripts/verify.py
```

`local_tests.status: PASS`는 지금 구현된 테스트들이 통과했다는 뜻이다. `integration.status: BLOCKED`는 전체 에이전트/API 연결을 검증할 수 없다는 뜻이다. 둘은 동시에 존재할 수 있다.

- JSON: 테스트 수, 실패/오류/skip 수, 실행 시각, 커밋, dirty 여부, 통합 차단 파일 목록.
- JUnit: CI가 읽는 개별 테스트 결과.
- 로그: 실패 원인과 pytest 출력을 확인할 근거.
- 테스트가 하나도 실행되지 않았거나 전부 skip된 경우에는 통과로 기록하지 않는다.
- pytest 실행 시간은 응급실 추천 P90이 아니다. 후보 정확도 90%, P90 15초는 여전히 미측정이다.

최신 테스트 개수와 검증 범위는 [verification.md](verification.md)에 기록한다. CI 구성 파일을 만들었다는 것과 GitHub에서 실제 실행 성공했다는 것도 구분한다.

## 팀에 요청할 다음 작업

가장 먼저 1번과 `chat → 결과`, `approve → 저장 결과`, `reset/forget`, 119 우선 이벤트의 계약을 맞춘다. 그 다음 2·3·5번이 합쳐진 runner 어댑터를 연결하고 합성 화면 대신 실제 모듈 시나리오를 검증한다. 자세한 확인 목록은 [ui-integration.md](ui-integration.md)에 있다.

4번과도 전체 삭제/저장 수명 규약을 확인한다. 현재 도보 반경 문서가 서로 다른 문제는 3번이 확정해야 한다. 6번은 화면에서 반경 확대 규칙을 따로 구현하지 않는다.

## 발표에서 말할 수 있는 문장

> 저는 Streamlit 사용자 흐름과 통합 검증 기반을 맡았습니다. 가상 데이터를 사용해 결과 카드, 브라우저별 대화 분리, 기존 메모리 모듈의 승인·거절과 데이터 삭제를 연결했습니다. 재실행과 설정 변경에서 오래된 승인이나 중복 저장이 발생하지 않는지 자동 테스트로 검사하고, 테스트 실행 결과와 아직 연결되지 않은 기능을 분리해 보고하도록 만들었습니다. 실제 API와 전체 에이전트 성능 검증은 백엔드 연결 후 진행할 단계입니다.

AppTest 사용 방식은 [Streamlit 공식 문서](https://docs.streamlit.io/develop/concepts/app-testing)를 참고한다. AppTest는 Python에서 앱 이벤트와 출력을 검사하며, 실제 브라우저 외관 점검은 별도로 수행한다.
